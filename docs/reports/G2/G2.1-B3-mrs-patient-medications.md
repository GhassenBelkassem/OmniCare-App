## 2. Plan findings: how medications are stored and read today
- **Storage:** one `MEDICATION_STATEMENT` series per prescription item, projected by G-1's projector from a **signed** prescription. Migration 000018 enforces it:
  - `consultation_id NOT NULL`;
  - a provenance row in `mrs_medication_statement_sources`, validated against the signed prescription;
  - provenance cannot be changed afterwards.
- **No patient write exists**, and the public record write refuses this type (`records/service.go:131`).
- **The read** is `GET /internal/mrs/patients/{id}/medications` → `medications.Service.List` (`medications/service.go`):
  - it decrypts every statement and checks its provenance;
  - it groups statements into `current` (ACTIVE, expected end not passed) and `past`;
  - **callers:** Spring FT-1 (`HttpMrsPatientRecordClient.medications`, scope `FULL_PASSPORT`) and professionals with grants. The doctor chart has its own route (`doctor-chart/medications`, G-1) and is untouched.
- **Merged-read design:** keep `current` / `past` exactly as they are. Add the declared items in **separate fields**, because Spring maps every `current` / `past` entry as a prescription (`payload.medication…`). Putting declared items there would turn them into fake prescriptions in the app.
- **Migration:** item records need no SQL. `record_type` has no CHECK, and `DELETED` is an existing status. The list status is health data, so it lives in an encrypted `MEDICATION_LIST` record, and the database must guarantee at most one ACTIVE list per Patient. I chose a **partial unique index** (000041) over extending 000032's singleton-head functions: append-only, one statement, no rewrite of existing trigger functions.

## 3. Format and input limits

### 3.1 Records (encrypted payloads, schema v1)
```
PATIENT_MEDICATION: {item_id (= record series id), name, dosage_text?, times_per_day?,
                     duration? {value, unit: DAY|WEEK|MONTH}, started_on? (YYYY-MM-DD),
                     author_type: "PATIENT", author_id, source: "PATIENT_DECLARED",
                     created_at, updated_at}
MEDICATION_LIST:    {status: UNKNOWN|NONE_KNOWN|LIST, version (= record version)}
```
- **Edit and delete:** an edit writes the item's next version (`created_at` kept). A delete marks the current version `DELETED`; the encrypted history stays, and nothing reads deleted rows.
- **Stored checks:** they refuse `author_type ≠ PATIENT` and `source ≠ PATIENT_DECLARED`, so a stored declared item can never pose as a prescription. Re-validating a stored payload gives the same bytes.
- **Generic write blocked:** the generic record write refuses both types (`ErrAccessDenied`, before audit), as it does for `MEDICATION_STATEMENT` (R1).

### 3.2 Input limits. Errors give the path (`items.<i>.<field>`), a code and the bounds, never the value
These are input limits, not dosing rules: no clinical judgement in code.

| Field | Rule | Code |
|---|---|---|
| `items` | missing → refused (`[]` is the explicit « aucun »); more than 50 | `REQUIRED` / `TOO_MANY_ITEMS` (max 50) |
| `name` | trimmed, NFC; no control or bidi characters; 1–160 characters | `REQUIRED` / `INVALID_VALUE` / `TOO_LONG` (max 160) |
| `name` duplicate | case-insensitive, among the requested set (= the patient's declared items) | `DUPLICATE` |
| `dosage_text` | optional, same text rule, ≤ 80 characters | `INVALID_VALUE` / `TOO_LONG` (max 80) |
| `times_per_day` | 1–6 | `OUT_OF_RANGE` (min 1, max 6) |
| `duration.value` | 1–365 | `OUT_OF_RANGE` (min 1, max 365) |
| `duration.unit` | DAY, WEEK or MONTH (case-insensitive) | `REQUIRED` / `INVALID_VALUE` |
| `started_on` | YYYY-MM-DD, **not after today in Africa/Tunis** | `INVALID_DATE` / `OUT_OF_RANGE` |
| `item_id` | UUID, not repeated | `INVALID_VALUE` / `DUPLICATE` |
| `expected_version` | required, ≥ 0 | `REQUIRED` / `OUT_OF_RANGE` |

## 4. Route contract

### 4.1 `PUT /internal/mrs/patients/{mrsPatientID}/medications/declared`
- **Headers:** signed; `X-Actor-Role: PATIENT`; `X-Purpose: SELF_SERVICE` (main user) or `FAMILY_MANAGEMENT` (family member); `X-Scope: FULL_PASSPORT` (the scope Spring's FT-1 medication read already sends); `Idempotency-Key`.
```json
{"items": [{"item_id": "…optional", "name": "…", "dosage_text": "…", "times_per_day": 2,
            "duration": {"value": 10, "unit": "DAY"}, "started_on": "2026-11-01"}],
 "expected_version": 3}
```
- **200:** `{record_id, record_version, section: "MEDICATIONS", version, warnings: []}`. `version` is the new list version to expect next. Ids and versions only (also the replay body).
- **Semantics:**
  - **the body is the desired set of the patient's declared items:** `item_id` of a declared item → update; no `item_id` → new item; a declared item left out → deleted;
  - an unchanged item is not rewritten;
  - prescriptions are never touched.
- **Why one list PUT rather than add/edit/delete routes:**
  - it matches B2 (same semantics, error codes and client code);
  - the editor saves everything with one « Enregistrer », and the PUT is atomic, so there is never a half-saved editor;
  - one version check, one key and one audit row per save;
  - the NONE_KNOWN rule ("after a patient edit") applies naturally.

### 4.2 List status (ADR-012 rule 4) and version
- **On write:**
  - no declared item **and** no current prescription → `NONE_KNOWN`;
  - otherwise `LIST`.
  - "Current prescription" uses the medication read's own rule (`CountCurrentPrescriptions`, injected, so the rule lives in one place).
- **Version:** `MEDICATION_LIST` record version; 0 before the first save. A stale `expected_version` → 409 with `current_version` only.
- **On read:** `LIST` whenever a current item exists (prescription or declared), because a doctor may have prescribed since the patient's last edit. Otherwise the stored status, or `UNKNOWN` if the list was never saved. Tested: NONE_KNOWN + a new prescription reads LIST with the version unchanged.

### 4.3 Error codes (same shapes as B2)
| Case | HTTP | `error.code` |
|---|---|---|
| Field limits (§3.2) | 422 | `INVALID_MEDICAL_PAYLOAD` + `fields[{path, code, min?, max?}]` |
| `item_id` of an OmniCare prescription (statement id or series id) | 422 | `ITEM_LOCKED` |
| `item_id` unknown for this subject | 404 | `RESOURCE_NOT_FOUND` |
| Subject missing, not held, or not ACTIVE | 404 | `RESOURCE_NOT_FOUND` (same body, R2) |
| `expected_version` ≠ list version | 409 | `RECORD_VERSION_CONFLICT` + `current_version` |
| Same key, different body / still running | 409 | `IDEMPOTENCY_CONFLICT` / `IDEMPOTENCY_IN_PROGRESS` |
| Wrong role, purpose, scope; purpose ≠ subject kind; missing key | 400 | `INVALID_INTERNAL_REQUEST` / `INVALID_IDEMPOTENCY_KEY` |
| `author_type`, `author_id`, `source` or any unknown field in the body | 400 | strict decoder (R1) |
| Key, audit or other failures | 503 / 503 / 500 | `MRS_KEY_UNAVAILABLE` / `AUDIT_UNAVAILABLE` / `INTERNAL_ERROR` (logged with a fixed message) |

- **Idempotency (R4):** the stored key is `hash(actor, subject, MEDICATIONS, key)`. A replay returns the first result and writes nothing.
- **Audit (R7, R9):** `PATIENT_MEDICAL_DATA_WRITE`, scope `MEDICATIONS`, purpose SELF_SERVICE / FAMILY_MANAGEMENT, record id on success, failure code otherwise. Identifiers only.
- **Locks:** idempotency → patient row → list record → declared items, all in one transaction; synchronous (D5).

## 5. Merged read: `GET …/medications` (additive)

### 5.1 New fields, and what Spring must map in SB1
| Field | Where | Meaning |
|---|---|---|
| `source` | each `current[]` / `past[]` entry | always `PRESCRIPTION` |
| `author_type` | each `current[]` / `past[]` entry | always `PROFESSIONAL` (read-only for the patient) |
| `declared_current[]`, `declared_past[]` | top level, **patient and SYSTEM reads only** | `{item_id, record_version, name, dosage_text?, times_per_day?, duration?{value, unit}, started_on?, expected_end_on?, source: "PATIENT_DECLARED", author_type: "PATIENT", created_at, updated_at}`. `author_id` stays internal |
| `list_status` | top level, patient and SYSTEM | `UNKNOWN` / `NONE_KNOWN` / `LIST` (§4.2) |
| `list_version` | top level, patient and SYSTEM | the `expected_version` of the next PUT |

- **Spring keeps parsing:** Spring's `MedicationList` / `MedicationStatement` records are `@JsonIgnoreProperties(ignoreUnknown = true)` and read only `current` / `past` (`MrsPatientRecordClient.java:38-53`). The existing fields are unchanged, and a professional read keeps exactly the old top level (`TestMedicationListShapeIsAdditive`).
- **SB1 work:**
  - map the new fields into `GET /api/v1/me/medical-record/medications`, which today pages `current` / `past` by `group`. Declared items join the same `CURRENT` / `PAST` groups, flagged « Déclaré par le patient »;
  - return `list_status` and `list_version`;
  - add the write route calling §4.1.

### 5.2 Current or past for a declared item (Africa/Tunis, UTC+01:00, no daylight saving: the same rule as the app)
- **No duration:** current until deleted.
- **With a duration:** `expected_end_on` = `started_on` (or the Tunis date it was declared) + duration − 1 day, inclusive. Months clamp to the month's last day, so 31 January + 1 month ends on 27 February, never in March.
- **The rule:** current while today (Tunis) ≤ `expected_end_on`. Tested at the boundary: 22:59:59 UTC on the last day is current; 23:00:00 UTC, which is Tunis midnight, is past.

### 5.3 Professionals
Declared items and the list status are **not** added to professional reads of this route. ADR-012 rule 5 wants doctors to see them labelled « Déclaré par le patient ». How and where (workspace, chart) is G-1's display work, so it joins B4, together with rule 6 (life-safety visibility). No new disclosure path was opened here.

## 7. Findings to know
1. **Parallel test flake, G-1's test:**
   - `prescriptions.TestConsultationPrescriptionWorkflowCASFinalizationAndPatientRead` counts idempotency rows across the **whole database**, so it fails when another package writes at the same time under `go test ./...`.
   - It passes alone (3/3) and with `-p 1`.
   - Recommend G-1 scopes its counts to its own patient, or CI runs `-p 1`.
2. **Migration number:** 000041 is the next free number here. Another session's 000040 is still uncommitted; if another branch also adds a 000041, renumber at commit time.
3. **Date conventions:** prescriptions' current/past (G-1's existing `medicationDisplayStatus`) compares UTC dates; declared items use Tunis dates as specified. For one hour a day (00:00–01:00 Tunis) a prescription ending "yesterday UTC" can differ by a day from a declared item. This is G-1's rule; the fix is to share `records.TunisDate` (B4).
4. **ITEM_LOCKED for prescriptions** matches either the statement id or its series id. Spring today exposes `medication_statement_id` to the app, so both work.
