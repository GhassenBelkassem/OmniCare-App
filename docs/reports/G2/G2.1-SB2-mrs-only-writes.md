## 3. What moved (Part 1)

**New: `patientrecord/application/PatientMedicalDataUpdates.java`.** This is the server-side caller of the SB1 write service (a Java call, not HTTP). For each section it:
1. reads the section's **current version** just before writing (`expectedVersion`);
2. keeps the ids of the patient's own items, matched by label (case-insensitive), so a repeat doesn't churn ids;
3. leaves out a label a professional already recorded (MRS keeps it; resending it would be a DUPLICATE);
4. uses a **fresh server-made Idempotency-Key** (UUID v4);
5. calls `PatientMedicalDataWriteService` (SB1), which resolves the subject, sends the purpose (SELF_SERVICE / FAMILY_MANAGEMENT) and maps MRS errors;
6. renames field errors to the caller's field names (§3c).

**Why a server-made key is safe here:**
- The legacy routes carry no client key.
- Every list write sends the **desired set**, so the same request twice leaves the same section.
- A scalar write is skipped when the stored value is already the requested one (tested: a repeated passport PATCH writes nothing).
- A real concurrent change is caught by `expectedVersion`.

**No silent retry:** a 409 is returned as `RECORD_VERSION_CONFLICT` in the shared envelope.

**Transactions (R8):** the MRS call always runs outside any DB transaction.

| Route | Request / response shape | Inside now |
|---|---|---|
| Onboarding steps 1–4, skip | **unchanged** | **Step check:** a short read, then the MRS section writes (no transaction), then a short `TransactionTemplate` commit of the step and completion; a concurrent duplicate commits once. **Step 1:** identity stays in Spring; blood type / height / weight (if sent) go to MRS. **Steps 2–4:** §4. **Completion %:** from MRS (blood type 20, measurements 15, allergies 20, conditions 15, declared medications 15; step 4 = 100 as before) |
| `PATCH /profile/passport` | unchanged (`ProfileResponse`) | blood type and measurements sections (SELF). A value left out keeps the stored one; MRS merges height and weight, so one can be sent alone |
| `PATCH /profile/family-members/{id}/passport` | unchanged (`FamilyMemberResponse`) | the member's MRS record is ensured in a short transaction (unchanged), then the same writes as **FAMILY_MANAGEMENT** on the member's record only |
| `PATCH /profile/medical-data` | unchanged (`MedicalDataResponse`, 202) | blood type, allergies (labels), `criticalConditions` → life-safety conditions (they are critical by name), measurements. An empty list records NONE_KNOWN. Not called by the current app |
| `GET /profile/medical-data` | unchanged | **the same MRS v3 read** as `GET /me/medical-record/medical-data` (`PatientMedicalRecordService.medicalData`). `syncOperationIds: []`, `syncStatus: "COMPLETED"`, because writes are synchronous. **Fixes SB1's stale-data P1** (tested) |

## 5. ⛔ STOP 3: critical conditions

**What MRS v3 does:**
- `ItemV3` has `item_id`, `label`, author, dates and `severity`, and **no critical / opt-in flag** (`records/life_safety_v3.go`).
- The doctor reads put **every** life-safety condition into `critical_conditions`:
  - `workspace/model.go:49-54` (`EssentialInformationOf`);
  - `chartclinical/service.go:226`.
- That view is always visible to a treating doctor, and the lock toggle hides consultations only (ADR-012 rule 6, ADR-003 §7.2).
- MRS has no other record type for an ordinary condition.

**So:**
- Sending ALL onboarding conditions would make every one always visible: a rule-6 breach.
- Today's meaning is kept: only `criticalOptIn=true` conditions are written. The editor's (SB1) conditions section is life-safety by definition.
- Nothing else changed: no doctor code, no MRS model.

**Smallest change (needs a decision; G-1 owns the doctor views):**
1. **MRS (B-step, additive):**
   - add `critical bool` to each condition item;
   - v1/v2 conditions upcast as `critical=true`, since they came from the opt-in;
   - new patient conditions default to `false`;
   - SB1 `PUT …/conditions` gets an optional `critical` per item, and the read returns it.
2. **G-1:** `EssentialInformationOf` and `chartclinical` keep only `critical=true` items in `critical_conditions`. Non-critical conditions show only under the patient's sharing rules (FULL_PASSPORT), like other history.
3. **Spring:** onboarding sends ALL conditions with `critical = criticalOptIn`.
4. **App (A2/A3):** the editor and onboarding show « Visible en urgence » per condition, default off.

**Until then:**
- an onboarding condition does not appear in « Dossier médical », in either the old or the new code;
- the manual test below says so;
- the editor's conditions are critical ones.

## 6. Pending outbox rows (no manual SQL)

- **Medical-data kinds that can be pending: 2.**
  - `LIFE_SAFETY` (actor PATIENT; v1 arrays or v2 three-state payloads);
  - `BODY_MEASUREMENTS` (actor PATIENT, v1).
- **No new rows can appear:** `MrsSyncOutboxService.enqueueRecord(…PATIENT…)` has no caller left. Its only caller was `MrsMedicalDataService.store`, now removed.
- **Spring retires them:** `MrsSyncOutboxWorker` closes any claimed PATIENT job of those 2 types **before** calling MRS (`MrsSyncOutboxWorker.java:59,147-166`). The job ends `DEAD_LETTER` with reason `PATIENT_MEDICAL_WRITE_RETIRED` on the next poll (tested: the MRS client is never called).
- **An admin requeue** is retired again on the next poll.
- **MRS refuses them too** (Part 2), so even a stray call cannot replace a v3 record.
- **Not counted:** I have no access to a live database, so the number of pending rows was not counted. The worker handles all of them, whatever the count.
- **Unchanged:** professional jobs (`CONSULTATION_RECORD`, `NURSE_VISIT_RECORD`, actor SYSTEM) are not singleton types and keep being processed (existing test green).

## 7. Part 2: omnicare-mrs

**Every caller of `PUT /internal/mrs/patients/{id}/singleton-records/{type}`:**
- **production:** only Spring `HttpMrsMedicalRecordClient.upsertSingleton`, through the outbox worker, as PATIENT. That path is retired (§6). No Spring code queues a SYSTEM singleton job; the professional jobs are not singleton types.
- **not this route:** the admin `…/reconcile` route is separate and unchanged. G-1's consultation write is an in-process Go call (`ApplyConsultationMedicalSummary`).
- **tests:** several MRS tests seed legacy records through the **service** method `records.Service.UpsertSingleton` as PATIENT. Some are G-1's (`completion/p2a_fence_integration_test.go`, read-only for me), the others are `chartclinical` and `records` tests.

So the refusal is at the **HTTP route**, where `X-Actor-Role` lives (`api/medical_records.go:659-670`):
- PATIENT on LIFE_SAFETY or BODY_MEASUREMENTS → **422 `PATIENT_SECTION_ROUTE_REQUIRED`**, before the body is read;
- other roles reach the unchanged service.

No non-patient caller breaks, so there was no STOP.

**Tests** (`api/singleton_patient_refusal_test.go`):
- **patient refused:** LIFE_SAFETY (also lower-case in the path) and BODY_MEASUREMENTS, with a nil service to prove nothing is read;
- **SYSTEM:** passes the route into the service;

- **Suite:** `gofmt -l` empty, `go vet ./...` clean, and `go test -p 1 -count=1 ./...` on a throwaway postgres:16 (since removed). Every package passes except the **2 failures that predate B1**: the artifacts certificate check and ClamAV EICAR.

## 10. Risks and findings
1. **⛔ STOP 3 (§5):** onboarding conditions stay out of MRS until the critical flag exists. Decision needed; it is a G-1 + MRS + app change.
2. **Onboarding medication fields:** `frequency` (fixed `'1x daily'`) and `startDate` (the onboarding day) are not patient answers. A3 should either ask for them or stop sending them. `timesPerDay` and `startedOn` stay empty until then.
3. **Completion %:** it no longer counts non-critical conditions, since they aren't stored. A profile with only such conditions scores 15 points less than before.
4. **`PATCH /profile/medical-data`:** an empty list now records NONE_KNOWN (desired-set semantics) where it used to leave UNKNOWN. The current app doesn't call this route.
5. **Old data:** values that exist only in the legacy columns or `passport_*` tables (accounts that never synced) are no longer shown. In practice, the onboarding sync always wrote them to MRS and cleared the columns (`0202-mrs-medical-source-of-truth.yaml`). The audited purge before launch should count any leftovers first.
6. **R11:** no new rate limit. These routes are as limited as before.
