## 4. MRS gap against ADR-012

How it is stored today: all clinical data is encrypted JSON in `medical_records`. LIFE_SAFETY and BODY_MEASUREMENTS are singletons (`mrs/migrations/sql/000032:9,124`). Migrations are `sql/*.up.sql`, recorded in `mrs_schema_migrations(version, applied_at)` (`mrs/migrations/migrations.go:14,39-117`), append-only by convention. The latest is **000040**.

| ADR-012 need | Today | Change needed |
|---|---|---|
| Rule 3: author type per allergy, condition, medication | ❌ Plain `items []string`. Only record-level `source{CONSULTATION,…}` and `created_by_actor_id`, with no role (`life_safety_v2.go:44-63`) | **LIFE_SAFETY v3** (payload only, no SQL): `bloodType{value, authorType, setAt}` and `allergies` / `conditions{status, version, items[{itemId, label, authorType, severity?}]}`. v1 and v2 are read as v3 at read time |
| Rule 3: blood type locked once set by a professional | ❌ The patient PUT can overwrite it | Enforced in the new patient section route |
| Rule 4: lists UNKNOWN / NONE_KNOWN / LIST | ✅ for allergies and conditions (v2). ❌ for medications | Medication list status: either a new singleton type (**000041** re-creates the record-type CHECK `000032:9` and the trigger `000032:110-154`), or a field in v3 |
| Rule 4: untouched section unchanged; emptied → NONE_KNOWN | ❌ The PUT replaces the whole payload, and LIST with 0 items is rejected (`life_safety_v2.go:125-149`) | Section routes; an emptied list becomes NONE_KNOWN on the server |
| Rule 5: PATIENT_DECLARED medications | ❌ Only `MEDICATION_STATEMENT` from signed prescriptions (`mrs/medications/projector.go:241-297`; triggers `000018`) | New record type `PATIENT_MEDICATION` (`record_type` has no CHECK, so no SQL), one series per item. The medication read merges both types and exposes `source` |
| Rule 6: life-safety data can't be hidden | ❌ The doctor workspace hides ESSENTIAL_INFORMATION and CURRENT_MEDICATIONS unless policy flags are on, and they default to off (`mrs/workspace/repository.go:118-130`; `workspace/service.go:187-226`; `000022:11-12`) | Stop gating life-safety in workspace (code only). **Owner: G-1** (workspace) |
| Rule 7: per-section version + 409 | ❌ One version for the whole record. `ExpectedRecordVersion` exists but the PUT doesn't pass it (`medical_records.go:666-670`); `UpsertSingletonDelegated` has no caller (`audited_service.go:130`) | Version per section inside v3 (optional table `mrs_record_section_versions` in 000041). Wire expected-version → `RECORD_VERSION_CONFLICT` |
| Rule 7: Idempotency-Key, audit | ✅ Idempotency store (8-200 characters, 24 h, replay, `mrs/api/idempotency.go:8-20`). ✅ Audit runner ATTEMPTED/COMPLETED/FAILED (`mrs/audit/service.go:91-136`) | One audit operation per section |
| Rule 7: configurable ranges, soft warnings | ❌ Hard-coded 30-300 cm and above 0 up to 500 kg (`registry.go:311`), no field code, no warning concept | Ranges in config and `security-contract/clinical-limits.json`. A warning shape that never echoes values |
| Rule 2: same 404 | ⚠️ Patient record and documents return 403 for a missing patient or a non-owner (`mrs/patientrecord/repository.go:58-69`; `documents service_errors.go:565-569`). Spring already folds both into one 404 (`HttpMrsPatientRecordClient:99-107`) | Keep Spring as the single 404 point; new MRS routes return 404 |

**G-1 writes that must stamp the author:**
- `ApplyConsultationMedicalSummary` (`mrs/records/life_safety_apply.go:90`) must write `authorType=PROFESSIONAL`.
- The consultation v4 summary merge (`life_safety_v2.go:165-183,234-248`) must keep the PATIENT items the doctor did not touch.
- The prescription projector already writes `source=PRESCRIPTION` (`projector.go:241-246`).
- The workspace and chart readers (`workspace/service.go:209-223`, `chartclinical/service.go:176`) must read v3.
- The `records` package is shared, so G-1 must review these changes.

**How I read rule 3 on existing items (overrule if wrong):**
- An item in a record with `source=CONSULTATION` is PROFESSIONAL.
- An item written through the patient singleton PUT by the account holder (`created_by_actor_id` = holder) is PATIENT.
- Anything else falls back to the ADR default, PROFESSIONAL.

Without this, items a patient already typed would become locked for that patient.

## 7. « Afficher le QR » and the share icon

- **QR 404: exact cause.** `sb/medicalsharing/MedicalSharingService.java:188-190`:
  - It looks up `findByRequesterUserIdAndStatus(actor, IN_PROGRESS)` and throws `RESOURCE_NOT_FOUND` when no consultation is in progress.
  - A subject that differs from the consultation's subject gives the same 404 (`:191-193`).
  - A new test patient has no consultation in progress, hence the 404.
- **It is by design:**
  - `P5-01_DOCTOR_CLINICAL_ARCHITECTURE_FREEZE.md:332` says Spring "verifies an eligible active Consultation/care context".
  - The release app already shows « QR disponible pendant une consultation. » with « Réessayer » (`app/features/patient_passport/sharing/medical_share_qr_controller.dart:141-142`). A debug build shows a labelled preview.
- **Ruled out:**
  - The app path matches the controller (`medical_share_qr_api.dart:28`, `PatientMedicalSharingController:32,91`).
  - MRS errors map to 503 or 409, never 404 (`HttpMrsMedicalShareClient:183-207`).
  - Every new account gets its MRS patient at signup (`UserProfileService.initializeProfile:44` → `HttpMrsPatientClient.createMainPatient:37-87`).
- **Owner: G-1.** There is nothing to fix unless the CTO wants a QR outside a consultation (D1).
- **Share icon:** `GET/PUT /patient/medical-sharing/policy`.
  - MRS creates the policy on first use (`mrs/sharing/service.go:63`), so it should work for a new account. That was not tried with the CTO's account (UNVERIFIED).
  - A 404 would mean the MRS patient is missing or not owned (`HttpMrsMedicalSharingClient:159-160`).
  - The SELF wording of that 404 and the server-text leak are G-1 hand-offs (§2 row 3).
