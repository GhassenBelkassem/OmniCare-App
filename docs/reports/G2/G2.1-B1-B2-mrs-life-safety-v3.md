## 3. B1: formats and validation

### 3.1 LIFE_SAFETY v3 (`records/life_safety_v3.go`)
```
blood_type: {value: A+|A-|B+|B-|AB+|AB-|O+|O-|UNKNOWN, author_type?, author_id?, set_at?, version}
allergies:  {status: UNKNOWN|NONE_KNOWN|LIST, version,
             items: [{item_id, label, author_type, author_id, created_at, updated_at, severity?}]}
conditions: same as allergies, without severity
author_type: PATIENT | PROFESSIONAL   (always the authenticated actor, R1)
```
- **Section version:** the record version at which the section last changed. It only grows: every write gets a higher record version, and a v1/v2 record reads every section at its own record version. An empty record reads version 0.
- **Read as v3 at read time** (`LifeSafetyV3Of`). Stored rows are never rewritten; the next patient write stores v3.
  - **Author rule** (task §B1.3, `legacyAuthor`): `source=CONSULTATION` → PROFESSIONAL (with the doctor's id); written by the account holder → PATIENT; anything else → PROFESSIONAL.
  - **Item ids:** stable, derived from the record id plus section plus position (a name-based UUID, version-5 layout). The app can therefore edit an upgraded item before it is ever stored as v3.
  - **Times:** `created_at` / `updated_at` / `set_at` = the record's creation time.
- **G-1 compatibility:** `ReadLifeSafety` gains a v3 case that returns labels only (`life_safety_v2.go`). The workspace, the chart and the consultation merge read v3 with no change.
- **Allergy severity:** codes `MILD | MODERATE | SEVERE`. Onboarding offers « légère », « modérée » and « sévère » (`conversational_onboarding_screen.dart:1265-1275`; Spring `OnboardingStepRequest.java:49`), so Spring maps légère → MILD, modérée → MODERATE, sévère → SEVERE. **REQUIRES MEDICAL VALIDATION.**

### 3.2 BODY_MEASUREMENTS v2 (`records/body_measurements_v2.go`)
`{height_cm?, weight_kg?, measured_at, author_type, author_id, version}`. At least one value must be present. The three v1 field names are unchanged, so the chart decoder keeps working (tested). v1 is read as v2 with the same author rule.

### 3.3 Validation (R6). Errors carry `path` + `code` (+ `min` / `max`), never the value
| Rule | Code |
|---|---|
| Label empty after trimming | `REQUIRED` |
| Label longer than 160 characters (NFC, counted in characters) | `TOO_LONG` (max 160) |
| Control character, bidi override/isolate (U+202A–E, U+2066–9), invalid UTF-8 | `INVALID_VALUE` |
| More than 50 items, professional ones included | `TOO_MANY_ITEMS` (max = room left) |
| Case-insensitive duplicate (Unicode case folding), in the request or against a professional item | `DUPLICATE` |
| Malformed or repeated `item_id` | `INVALID_VALUE` / `DUPLICATE` |
| Blood type not one of the 8 groups or UNKNOWN | `INVALID_VALUE` |
| Severity not MILD/MODERATE/SEVERE; any severity on a condition | `INVALID_VALUE` / `NOT_ALLOWED` |
| Height/weight outside the hard limits | `OUT_OF_RANGE` (min, max) |
| No height and no weight | `NO_CONTENT` |
| `items` missing (an empty list `[]` is the explicit « aucune connue ») | `REQUIRED` |
| `expected_version` missing or negative | `REQUIRED` / `OUT_OF_RANGE` |

- **Labels:** trimmed and NFC-normalised (`golang.org/x/text`, already in the module graph at the same version; go.mod only marks it direct, and go.sum is unchanged).
- **Stored-payload check:** it validates structure, enums, ids, times and length, but **not** control characters or duplicates. A professional label carried over from v1/v2 therefore never makes a record unreadable.

### 3.4 Configurable limits (ADR-012 rule 7)
| Variable | Default | Effect |
|---|---|---|
| `MRS_MEASUREMENT_HEIGHT_CM_MIN` / `_MAX` | 30 / 300 | Hard: refuse |
| `MRS_MEASUREMENT_WEIGHT_KG_MAX` | 500 (weight must be > 0) | Hard: refuse |
| `MRS_MEASUREMENT_HEIGHT_CM_USUAL`, `MRS_MEASUREMENT_WEIGHT_KG_USUAL` | empty (no warning) | Soft "min-max": stored, response `warnings: ["HEIGHT_UNUSUAL" / "WEIGHT_UNUSUAL"]`. **REQUIRES MEDICAL VALIDATION** before setting |

- **Narrow only:** hard limits can only narrow today's bounds; MRS refuses to start otherwise (`MeasurementLimits.Validate`). A stored value therefore always stays readable.
- **Not in the shared contract:** I did not add these to `security-contract/clinical-limits.json`. Spring asserts that file, and this task makes no Spring change. SB1 adds them there together with Spring's Bean Validation.

## 4. B2: route contract
All routes are under `/internal/mrs/patients/{mrsPatientID}` and signed (existing middleware). Required headers:
- `X-Actor-Role: PATIENT`;
- `X-Purpose: SELF_SERVICE` (main user) or `FAMILY_MANAGEMENT` (family member);
- `X-Scope` as listed below;
- `X-Subject-Mrs-Patient-Id` equal to the path id.

JSON is snake_case (MRS convention). Writes also need `Idempotency-Key` (8–200 characters).

| Route | Scope | Body | 200 response |
|---|---|---|---|
| `GET /life-safety` | `LIFE_SAFETY_ONLY` | — | `{schema_version: 3, blood_type{value, author_type?, set_at?, version}, allergies{status, version, items[{item_id, label, author_type, created_at, updated_at, severity?}]}, conditions{…}}` |
| `PUT /life-safety/blood-type` | `LIFE_SAFETY_ONLY` | `{value, expected_version}` | `{record_id, record_version, section, version, warnings: []}` |
| `PUT /life-safety/allergies` | `LIFE_SAFETY_ONLY` | `{items: [{item_id?, label, severity?}], expected_version}` | same |
| `PUT /life-safety/conditions` | `LIFE_SAFETY_ONLY` | `{items: [{item_id?, label}], expected_version}` | same |
| `GET /body-measurements` | `FULL_PASSPORT` | — | `{height_cm?, weight_kg?, measured_at?, author_type?, version}` (`{version: 0}` when none) |
| `PUT /body-measurements` | `FULL_PASSPORT` | `{height_cm?, weight_kg?, expected_version}`; `measured_at` = server time | same, plus `warnings` |

- **Semantics** (ADR-012 rules 3–4):
  - **The list body is the desired set of the patient's own items:** `item_id` present → update that own item; absent → new item; an own item left out → deleted.
  - **PROFESSIONAL items stay in place, untouched.**
  - **After the write:** no item left → `NONE_KNOWN`; otherwise `LIST`.
  - **Other sections are never touched,** byte for byte, version included (tested).
- **Never returned:** `author_id` stays internal (minimisation). Write responses carry ids, versions and warning codes only, which is also the replay body.

### Error codes
| Case | HTTP | Body |
|---|---|---|
| Validation (§3.3) | 422 | `{"error":{"code":"INVALID_MEDICAL_PAYLOAD","fields":[{"path","code","min?","max?"}]}}` |
| `expected_version` ≠ current section version | 409 | `{"error":{"code":"RECORD_VERSION_CONFLICT","current_version":N}}`: code and version only (R5) |
| `item_id` of a PROFESSIONAL item | 422 | `ITEM_LOCKED` |
| Blood type last set by a PROFESSIONAL | 422 | `BLOOD_TYPE_LOCKED` |
| `item_id` not in this subject's section | 404 | `RESOURCE_NOT_FOUND` |
| Subject missing, not held by the actor, or not ACTIVE (deleted/shredded member) | 404 | `RESOURCE_NOT_FOUND`, the same body (R2) |
| Wrong role, purpose or scope; purpose not matching the subject kind | 400 | `INVALID_INTERNAL_REQUEST` |
| Missing or invalid key | 400 | `INVALID_IDEMPOTENCY_KEY` |
| Same key, different body | 409 | `IDEMPOTENCY_CONFLICT` |
| Same key still running | 409 | `IDEMPOTENCY_IN_PROGRESS` |
| Unknown field in the body (e.g. `author_type`, R1) | 400 | strict decoder |
| Key, audit or other failures | 503 / 503 / 500 | `MRS_KEY_UNAVAILABLE` / `AUDIT_UNAVAILABLE` / `INTERNAL_ERROR`, logged with a fixed message only |

The locks use 422, not 409. The app's 409 means « Votre dossier a été modifié ailleurs, rechargez », whereas a lock is permanent.

- **Idempotency (R4):** the stored key is `hash(actor, subject, section, Idempotency-Key)`, with one operation per section. Two callers or two subjects can never collide. A replay returns the first result and writes nothing (tested).
- **Audit (R7, R9):**
  - **Each write:** ATTEMPTED, then COMPLETED or FAILED under the operation `PATIENT_MEDICAL_DATA_WRITE`, with actor, role, patient, `purpose` (SELF_SERVICE / FAMILY_MANAGEMENT), `scope` = section, the record id on success, and failure codes such as `VALIDATION_FAILED`, `RECORD_VERSION_CONFLICT`, `ITEM_LOCKED`, `BLOOD_TYPE_LOCKED`, `SUBJECT_NOT_FOUND` or `PURPOSE_SUBJECT_MISMATCH`.
  - **Author type:** the operation type itself means "patient-authored" (G-1's writes use `LIFE_SAFETY_CONSULTATION_UPDATE`), so the audit table needed no new column.
  - **Reads:** audited as `LIFE_SAFETY_READ` / `PASSPORT_READ` plus `MRS_DECRYPT`.
- **Ordering and locks:** idempotency reservation → patient row lock → singleton head lock. This is the same order as the existing writes, so there is no new deadlock path.

## 5. The old singleton PUT (kept working)
`PUT …/singleton-records/{LIFE_SAFETY|BODY_MEASUREMENTS}` is unchanged for v1/v2. It now refuses LIFE_SAFETY v3 and BODY_MEASUREMENTS v2 (`UNSUPPORTED_SCHEMA_VERSION`), so no client can send `author_type` (R1).

**Its callers today:** all go through `MrsMedicalDataService` → outbox → `MrsSyncOutboxWorker:70` → `HttpMrsMedicalRecordClient.upsertSingleton`, with role PATIENT:
- `PATCH /profile/passport` (`UserProfileService.java:94`);
- `PATCH /profile/family-members/{id}/passport` (`FamilyMemberService.java:141`);
- `PATCH /profile/medical-data` (`UserProfileService.java:159`);
- onboarding step 4 and skip (`MrsOnboardingSyncService.java:35,60,72`).

No professional path writes these types.

**Gap until SB2:** this route replaces the whole record. Over a v3 record it can overwrite a professional's blood type or items, and everything it writes reads as PATIENT (holder-written). It is tested to keep working. SB2 removes these callers; after that, PATIENT access to this route should be closed.

**For SB1 (Spring):** Spring's current medical-data read goes through its own record-reference table and the generic `GET /records/{id}`. It cannot parse v3, and it does not know records written by the new routes. **SB1 must switch Spring's reads to `GET /life-safety` and `/body-measurements` in the same change that starts calling the PUT routes.**

## 6. STOP point: G-1's consultation write over v3 (B4, G-1 owns it)
`records/life_safety_apply.go:83-90` (and the v4 merge, `life_safety_v2.go:74-80,165-183,234-248`) is read-only here. It keeps working over v3, which is tested (`TestG1ConsultationWriteOverV3StillParses`). But it reads labels only and writes **v2** with `source=CONSULTATION`, so after any finalization:
1. **every PATIENT item becomes PROFESSIONAL**, even in sections the doctor did not touch. The patient then gets `ITEM_LOCKED` on his own entries;
2. **every item id changes**, because ids are re-derived from the new record, so ids the app holds give 404;
3. **a blood type the patient set becomes "set by a professional"** → `BLOOD_TYPE_LOCKED`, even if the doctor did not change it;
4. **allergy severities are dropped** (v2 has none);
5. **every section version moves.** This is harmless: a pending patient edit gets 409 and reloads.

**What G-1 must change in B4:**
- **a.** In `ApplyConsultationMedicalSummary`, read the current record with `LifeSafetyV3Of(…, holderActorID)` and write **v3** with `LifeSafetyV3Payload` and `PatientLifeSafetySchemaVersion`.
- **b.** For a section the update leaves nil, copy it unchanged: items, ids, authors, severity, version.
- **c.** For a section the doctor changed:
  - existing items are matched by label (case-insensitive, `labelKey`) and keep their `item_id` and author;
  - new items get a new id, `author_type=PROFESSIONAL` and `author_id` = doctor;
  - items the doctor removed go;
  - the section version becomes the new record version;
  - status: no item → NONE_KNOWN, unless the doctor set UNKNOWN or NONE_KNOWN explicitly.
- **d.** Blood type: if changed → PROFESSIONAL plus doctor plus `set_at`; if unchanged → keep the author.
- **e.** Workspace and chart: read authors through `LifeSafetyV3Of` and show « Déclaré par le patient » for PATIENT items (ADR-012 §4); remove life-safety gating (rule 6, the P0 already handed off).
- **f.** Update `TestG1ConsultationWriteOverV3StillParses` to the new expectation.

**G-1 decision needed (not ours):** may a doctor remove a patient-declared item, and does "keeping" one confirm it as PROFESSIONAL? Recommendation: the doctor may remove it, the removal is audited, and a kept item stays PATIENT unless the doctor explicitly confirms it.

Until B4 ships, the app-facing editor (A2) works, but a consultation finalization locks the patient's earlier entries. B4 should land before A6 (acceptance).

## 9. Decisions to know
1. **Severity codes:** MILD/MODERATE/SEVERE rather than the French onboarding strings; Spring maps them (§3.1).
2. **Lock status:** the locks are 422, not 409 (§4).
3. **`measured_at`:** on a partial measurement update it is the time of that write, even for the value that was kept.
4. **Author rule holes:**
   - a v2 record written through the old route by the holder reads as PATIENT in full, including items that came from a doctor in an earlier version (the old route replaces everything);
   - this follows the CTO's rule as given; test accounts only (ADR-012 §1). It disappears once SB2 stops the old route.
5. **`author_id`:** stored but not returned by GET.
