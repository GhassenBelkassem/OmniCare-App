## 2. Plan: what I found before editing

### 2a. The current upload flow (old route `POST /api/v1/documents?patientId=`)
1. **Multipart in Spring:** `spring.servlet.multipart` sets 15 MB per file and 16 MB per request. `file-size-threshold` is not set, so the Spring Boot default of 0 applies: Tomcat writes **every part to a temp file on disk**, never to the heap.
2. **Init:** a JSON POST to MRS `…/documents/init` (type, file name, title, description, MIME). MRS answers with the document id and a one-time upload token.
3. **Content:** a POST of the raw bytes to `…/documents/{id}/content`, through `mrsDocumentRestClient`.
   - That client has **no interceptor** on purpose: Spring copies an intercepted request body into a byte array (`MrsClientConfiguration.java:47-51`).
   - The client reads the file twice, both times as a stream: once for the SHA-256 the signature covers, once to send it.
4. **Scan:** MRS stores the file and answers `SCAN_PENDING`. ClamAV runs in the background, and the app polls the FT-2 status route until `AVAILABLE` or `SCAN_FAILED`.
5. **What Spring holds in memory:** one 8 KiB buffer.
   - **But MRS buffers the whole file** (`api/documents.go` `readLimited` → `io.ReadAll`, up to 15 MiB). That is MRS code and out of scope here (§7.2).

**Why not reuse `HttpMrsDocumentClient`:**
- it always sends `SELF_SERVICE`, even for a family member;
- it flattens MRS codes: 409 and 410 both become `CONFLICT`, and 400 and 422 both become `INVALID_INPUT`.

Changing it would change the old routes and the doctor-chart upload. So a new client in `patientrecord/mrs` repeats the same init → digest → streamed-content steps, subject-aware and with MRS codes kept.

### 2c. The rate limiter
- **`SensitiveOperationRateLimiter`** (`shared/security`): a Redis fixed window, atomic in Lua, shared by every backend instance. It is already used by the medical-sharing QR and the phone-change OTP.
- **Reused** for pages: key `patient-record:document-page:<actorId>`, 60 per 1 minute.
- **Answer:** `TOO_MANY_REQUESTS` gets `Retry-After: 60` from `GlobalExceptionHandler`.

### 2d. CSRF (R10)
Same as SB1: the bearer token is in the `Authorization` header only, and there is no cookie session, so there is no CSRF surface. The new POST and DELETE matchers are PATIENT-only.

## 3. Decisions

### 3a. Routes and code layout
| File | Role |
|---|---|
| `patientrecord/api/PatientDocumentController` | the 4 routes; PATIENT only; sets the page headers |
| `patientrecord/application/PatientDocumentService` | order: parameters → subject (`RecordSubjects.resolve`, same 404) → MRS. Not `@Transactional` (R8) |

| `patientrecord/application/DocumentViewSessions` + `RedisDocumentViewSessions` | the server-side token store |
| `patientrecord/mrs/MrsPatientDocumentClient` + `HttpMrsPatientDocumentClient` | the signed MRS calls; 4xx → `MrsDocumentRejection(status, code)` |

### 3b. Upload: streamed, never buffered
- **The file part:** the `MultipartFile` (a temp file on disk) is handed to the client **as its own stream source**. Spring never calls `getBytes()` or `getResource()` (tested).
- **The client:** it reads that source twice as a stream (digest, then send), with an 8 KiB buffer. The second pass is a `Resource` with a fixed `contentLength`, so the message converter streams it with a fixed length and never counts the bytes by reading them.
- **Proof** (`HttpMrsPatientDocumentClientStreamingTest`, a real HTTP server):
  - the server reads the first byte of the content, then pauses;
  - the production client set-up had read **less than half** of a 48 MiB file at that moment;
  - the control, the same client with an interceptor, had read **all 48 MiB** first.

### 3c. Upload rules (all checked before the subject is resolved and before MRS is called)
| Field | Rule |
|---|---|
| `file` | present and not empty; ≤ 15 MiB (15,728,640 bytes, the MRS limit); the content type is `application/pdf`, `image/jpeg` or `image/png` **and** the extension matches (`.pdf`; `.jpg`/`.jpeg`; `.png`, any case). MRS re-checks the bytes (magic number, malformed file, PDF > 100 pages) |
| `title` | the SB1 text rule: trim, NFC, 1–160 code points, no control or bidi character. **Plus** ≤ 255 UTF-8 bytes, the MRS column limit (§7.1) |
| `documentType` | `LAB_RESULT`, `IMAGING`, `PRESCRIPTION_DOCUMENT`, `REFERRAL`, `DISCHARGE_SUMMARY`, `VACCINATION`, `OTHER_MEDICAL_DOCUMENT` (what the app sends today). The old French aliases (`analyse`, …) are not accepted |
| `documentDate` | optional; strict `YYYY-MM-DD`; not after today in **Africa/Tunis** (tested at the UTC/Tunis midnight boundary). MRS has no date field, so it travels in the encrypted description (`document_date=…`), as on the old route |

**The container limit:** a file over 15 MB is refused by Tomcat before the controller runs. `GlobalExceptionHandler` now answers on this one path with the same 400 the service gives (`file: TOO_LONG`). Every other upload route keeps its 413 `FILE_TOO_LARGE` (tested).

### 3d. Idempotency (R4)
- **Upload and delete:** the `Idempotency-Key` header is required and must be a UUID v4 (the SB1 check, reused).
- **Keys sent to MRS:** one per step, derived from the patient's key (`patient-document-init:` / `-content:` / `-delete:` + SHA-256). « Réessayer » with the same key replays the same MRS steps; the same key with a different file gives `IDEMPOTENCY_CONFLICT`.
- **View session:** no key from the app. Spring makes a new UUID per open, so a retried open is just a new 5-minute session.

### 3e. View sessions: the token stays server-side
- **Opening:** `POST …/view-sessions` calls MRS B5 route 1. The answer to the app is `{viewSessionId, pageCount, expiresAt}` only.
- **Storage:** the MRS `view_token` is stored in Redis under `patient-record:document-view:<actorId>:<viewSessionId>`, together with the document, the MRS record, the subject kind and the page count.
  - TTL = `expiresAt` − now, capped at 5 min. `expiresAt` is capped the same way.
  - An already-expired answer is refused (503).
- **Never logged:** every record that holds the token overrides `toString`.
- **A page request must match its session.** Checks, in this order:
  1. **Limit:** the page limit, before any lookup.
  2. **Subject:** the subject resolves (foreign → 404).
  3. **Session:** found under **this actor's** key. Unknown or expired → 410 (§7.6).
  4. **Match:** same document, same MRS record and subject kind, `n ≤ pageCount`. Otherwise → 404, and MRS is not called.
- **After MRS:** on MRS 410 or 404 the stored session is deleted.

### 3f. Page streaming and headers
- **Status first:** the controller writes a status and headers **only after** MRS answered 200 with a PNG for the page asked. Every failure before that is the normal JSON error.
- **Copy:** the PNG is copied in 8 KiB chunks (cut at 32 MiB).
- **Headers** (MRS B5 §5):
  - `Content-Type: image/png`, `Content-Disposition: inline`;
  - `X-Document-Page`, `X-Document-Page-Count`;
  - `Cache-Control: no-store, no-cache, must-revalidate, private, max-age=0`, `Pragma: no-cache`, `Expires: 0`;
  - `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; sandbox`;
  - `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Vary: Authorization`.

### 3g. Error mapping (MRS → API; never a value, R6)
| MRS | API |
|---|---|
| 404 (any code), 403 `DOCUMENT_ACCESS_DENIED` | 404 `RESOURCE_NOT_FOUND` (R2) |
| 409 `DOCUMENT_NOT_READY` | 409 `DOCUMENT_NOT_READY` (**new**) |
| 409 `IDEMPOTENCY_CONFLICT` / `IDEMPOTENCY_IN_PROGRESS` | the same codes (SB1) |
| 410 `VIEW_SESSION_EXPIRED` | 410 `VIEW_SESSION_EXPIRED` (**new**) |
| 413 `DOCUMENT_TOO_LARGE` | 400 `VALIDATION_ERROR`, `file: TOO_LONG` |
| 422 `INVALID_DOCUMENT` | 400 `VALIDATION_ERROR`, `file: INVALID_FORMAT` |
| 429 | 429 `TOO_MANY_REQUESTS` |
| 5xx, timeout, down, unreadable or inconsistent answer; 400/401 contract faults; 409 `PATIENT_KEY_UNAVAILABLE`/`INVALID_UPLOAD_STATE`; 410 `UPLOAD_SESSION_EXPIRED` | 503 `MRS_UNAVAILABLE`, `Retry-After: 30` |

### 3h. Audit and logs (R7, R9)
- **Purpose:** MRS audits each call with the purpose Spring sends, `SELF_SERVICE` or `FAMILY_MANAGEMENT` (fixed here; the old route always sent `SELF_SERVICE`).
- **Spring log lines:**
  - `patient_record_write section=DOCUMENT_UPLOAD|DOCUMENT_DELETE subject=… outcome=… code=…`
  - `patient_record_read section=DOCUMENT_VIEW|DOCUMENT_PAGE subject=… outcome=… code=…`
  - client lines: `mrs_patient_document op=… outcome=… status=… code=…`
- **Never in a log:** a token, a key, a title, a file name or an MRS id (log-capture test). The full test log of the run contains no view token either.

## 4. Contract for the app (A4)

**Common to every route:**
- **Access:** PATIENT only. Doctor → 403, no login → 401.
- **Subject:** the query parameter `subject=SELF|FAMILY:{familyMemberId}`, on every route including the multipart POST. The app never sends an MRS id.
- **Caching:** `Cache-Control: no-store`.
- **Common errors:**

| HTTP | Code | When |
|---|---|---|
| 400 | `VALIDATION_ERROR` | `fieldErrors` + `fieldErrorCodes` (table below) |
| 404 | `RESOURCE_NOT_FOUND` | foreign or unknown subject, document not yours, deleted or unknown: the same body every time |
| 409 | `CLINICAL_SUBJECT_UNAVAILABLE` | the subject has no record yet |
| 503 | `MRS_UNAVAILABLE` | MRS (or Redis) down; `Retry-After: 30` → « Réessayer » |

| Method · path | Request | Success | Route errors |
|---|---|---|---|
| `POST /api/v1/me/medical-record/documents` | `multipart/form-data`: `file` (part), `title`, `documentType`, `documentDate?`; header `Idempotency-Key` | **202** `{documentId, status:"SCAN_PENDING"}`, then poll `GET …/documents/{documentId}/status` (FT-2) until `AVAILABLE` or `SCAN_FAILED` | 400 (fields); 409 `IDEMPOTENCY_CONFLICT` (new key needed), `IDEMPOTENCY_IN_PROGRESS` (retry shortly, same key) |
| `DELETE /api/v1/me/medical-record/documents/{documentId}` | header `Idempotency-Key` | **204**, no body | 404; 409 `IDEMPOTENCY_*` |
| `POST /api/v1/me/medical-record/documents/{documentId}/view-sessions` | no body, no key | **201** `{viewSessionId, pageCount, expiresAt}` (≤ 5 min) | 404; 409 **`DOCUMENT_NOT_READY`** (« Document en cours d'analyse ») |
| `GET /api/v1/me/medical-record/documents/{documentId}/view-sessions/{viewSessionId}/pages/{n}` | `n` = 1..`pageCount` | **200** `image/png` (watermarked), headers of §3f | 410 **`VIEW_SESSION_EXPIRED`**: open a new session once, silently; 404 (document gone, or `n` > `pageCount`); 409 `DOCUMENT_NOT_READY`; **429 `TOO_MANY_REQUESTS`** (> 60 pages/min; `Retry-After: 60`) |
| any raw download | — | **none**: no route; the old `…/download` still answers 403 | |

**`fieldErrorCodes`:**

| Route | Field | Codes |
|---|---|---|
| all | `subject` | `REQUIRED`, `INVALID_FORMAT` |
| upload, delete | `Idempotency-Key` | `REQUIRED`, `INVALID_FORMAT` (not a UUID v4) |
| upload | `file` | `REQUIRED` (missing or empty), `TOO_LONG` (> 15 MiB), `INVALID_FORMAT` (not PDF/JPEG/PNG, extension does not match, unusable file name, or the bytes are not a valid file of that type) |
| upload | `title` | `REQUIRED`, `TOO_LONG` (> 160 characters, or > 255 bytes in UTF-8), `INVALID` (control or bidi character) |
| upload | `documentType` | `REQUIRED`, `INVALID_FORMAT` |
| upload | `documentDate` | `INVALID_FORMAT` (not `YYYY-MM-DD` or impossible date), `OUT_OF_RANGE` (after today, Africa/Tunis) |
| page | `page` | `INVALID_FORMAT` (not a number), `OUT_OF_RANGE` (< 1 or > 1000) |

Every broken upload field comes back in **one** answer, so the app can mark all of them at once.

**Notes for A4:**
- **Limit:** set the app's limit to 15 MB (it is still 20 MB, FT-2 §2c).
- **Fetching pages:** a page needs the `Authorization` header, so fetch it with the API client, not a plain image URL.
- **Memory:** keep only the pages on screen.
- **Retry:** on « Réessayer », send the **same** `Idempotency-Key` for the same upload or delete.

## 7. Risks, findings, not done

1. **Title length vs the MRS column (P2).**
   - MRS refuses a title over **255 bytes** (`upload_init.go:28`, Go `len`). A 160-character title with many accents or emoji can exceed that.
   - Spring now refuses it early with `TOO_LONG`, so the app gets a clear message instead of a 503. In practice, about 95+ accented characters.
   - Fix (MRS, later): count code points, or raise the limit to 640 bytes.
2. **MRS holds the whole file in memory** (`api/documents.go` `readLimited`, up to 15 MiB per upload). Spring streams, but MRS buffers. P2 for MRS: stream to the encrypted store.
3. **Redis down reads as `MRS_UNAVAILABLE`** (503, `Retry-After: 30`). The app shows the same « Réessayer », which is the right behaviour, but the code name is not exact. A generic `SERVICE_UNAVAILABLE` code would be cleaner; changing it later is additive.
4. **The view token sits in Redis in plain text** for at most 5 minutes. It is useless without Spring's MRS signing key (and mTLS in production). P3: encrypt it if Redis is ever shared.
5. **Fixed-window limit:** up to 120 pages can pass across a window boundary; every page request counts, including refused ones. That is acceptable for R11 (P2).
6. **An unknown session id answers 410, not 404.** An expired Redis entry and an id that never existed look the same, and 410 makes the app open a new session, which is the useful action. It reveals nothing: sessions are looked up under the caller's own key only.
7. **Upload answers 202** (the scan is still running), as the old route and MRS do. The final state comes from the FT-2 status route.
8. **MRS upload and delete** authorize on the holder relation only; they don't check the purpose against the subject kind (the B5 view routes do). Spring now sends the right purpose. G-1/MRS note only.
9. **The old routes** stay until A4 has moved the app. Then delete `DocumentController` (except `denyRawDownload`, or move it), `DocumentService`, the old DTOs, the three Spring tests listed in §2b, and the app's `DocumentsApi` + `FileRepository.createDocument`.
10. **Not done (out of scope):**
    - closing a session early (MRS revoke, optional per B5);
    - upload recovery on the new path. The same key replays both MRS steps, so it isn't needed for « Réessayer ».

**Manual test steps for the CTO:** none for this step (backend only). The checks run through the app in A4: upload, open, delete, a family member, a file over 15 MB, MRS stopped.
