**What each route needs** (contracts: SB1 §4, SB3 §4, FT-2 §6):
- **Section saves:**
  - a PUT with `subject`, `Idempotency-Key` (UUID v4) and `expectedVersion` (the section version from the last read);
  - a camelCase body without nulls, and never `authorType`/`source`;
  - 409 `RECORD_VERSION_CONFLICT` carries `currentVersion`.
- **Upload:** multipart `file` + `title` + `documentType` + `documentDate?`, with `subject` and a key; 202 `{documentId, status}`.
- **Delete:** DELETE with a key; 204.
- **View:** `POST …/view-sessions` → `{viewSessionId, pageCount, expiresAt}`; `GET …/pages/{n}` → PNG; 410 means open a new session.

## 3. Decisions

1. **Two new repositories; the read path is unchanged.**
   - `MedicalRecordWriteRepository` (sections) and `MedicalDocumentRepository` (documents) use the same `AppHttpClient`.
   - `MedicalRecordApiContract` is not extended: three test fakes implement it (FT-3, QR), and reads stay separate from writes.
   - Nothing is registered in `main.dart` yet: A2 and A4 add the view models that use these classes, so no unused provider exists.
2. **Read models are additive.** Every new field is optional with a default, so all existing callers and tests are unchanged:
   - `MedicalDataRecord`: `bloodTypeAuthor`, `bloodTypeVersion`, `allergyItems`/`allergiesVersion`, `conditionItems`/`conditionsVersion`, `measurementsAuthor`/`measurementsVersion`.
   - `RecordItem`: `itemId`, `label`, `author`, `severity`.
   - `MedicationRecord`: `source`, `author`, `itemId`, `duration`, `startedOn`, and `isDeclaredByPatient`.
   - `RecordPage`: `listStatus`, `listVersion` (medications only).
   - **Unknown values:** `RecordAuthor`, `AllergySeverity`, `MedicationSource`, `DurationUnit`, the document type and status all have an `unknown` value. `RecordAuthor.unknown` is **not editable** (only `patient` is), so an unexpected value can never unlock a professional item.
   - **Defaults:** a missing version reads as 0 (never recorded). An item without `itemId` or `label` fails the read.
3. **Idempotency: `SaveAttempt`, one per editor section and per document action.**
   - **The key:** `keyFor(fingerprint)` returns the pending key when the content is the same; otherwise it makes a new UUID v4.
   - **The fingerprint:** route + subject + exact body, built by the repository. So a change of content, of member or of `expectedVersion` (after a reload) always gives a new key.
   - **Dropped:** on success, on `IDEMPOTENCY_CONFLICT` (the key was used for other content), or on `reset()` (the editor calls it when the user edits).
   - **Kept:** any other failure (503, timeout, cancel), so « Réessayer » sends the same key.
4. **409 `RECORD_VERSION_CONFLICT`** becomes a `RecordVersionConflictFailure`: a subclass of `ApiFailure`, so it travels in `Err` like any failure, and carries `currentVersion`. A 409 without a version stays a plain conflict (it is not trusted, as in SB1).
5. **Upload source: a file path, or a stream on web (§7.1).** The CTO's check runs on `flutter run -d chrome`, and a browser file has no path. So there are two sources:
   - `PathDocumentSource`: Dio's `MultipartFile.fromFile` reads the file from disk in chunks;
   - `StreamDocumentSource`: `MultipartFile.fromStream` with a factory (for example `XFile.openRead`).

   In both cases the app keeps no `Uint8List` of the file. **Before any request**, the size (≤ 15 MiB, > 0) and the extension (pdf, jpg, jpeg, png, any case) are checked. A refusal comes back with **the server's shape**: `VALIDATION_ERROR`, `fieldErrors.file` = `tooLong` / `required` / `invalidFormat`. The file part's content type comes from the extension, so type and extension always match, as the server requires.
6. **Token refresh during an upload.** A multipart stream body cannot be replayed by the interceptor. The documents API rebuilds the request **once**, with the same key, when the refresh asks for it (`AuthReplayRequiredException`), as the old client did. Opening a view session works the same way. Delete and the section PUTs are declared idempotent writes, so the interceptor replays them itself.
7. **Pages, one at a time.**
   - **The request:** `GET` with `ResponseType.bytes`. One page is returned as a `Uint8List`, never the whole document.
   - **Error codes:** the error body of a bytes request arrives as bytes, so the API decodes it to text. That is how `VIEW_SESSION_EXPIRED`, `DOCUMENT_NOT_READY` and `TOO_MANY_REQUESTS` stay readable.
   - **On a 410:** `fetchPage` opens **one** new session and asks the page again. It returns the new session with the page, so the caller keeps using it. A second 410 is returned as a failure (3 requests, no loop). A page beyond the new session's `pageCount` gives a not-found without a request.
8. **Messages** (`presentation/medical_record_messages.dart`), from code + field path only:
   - `recordFailureMessage`: the 6 contract codes; anything else → the shared `apiFailureMessage` (unchanged behaviour, including `MRS_UNAVAILABLE` and the screen fallback).
   - `recordFieldMessage(field, kind)`: the path is read without indexes (`items[2].label` → `label`), then the table in §4.
     - INVALID gets « caractères non autorisés » **only on text fields** (`label`, `name`, `dosageText`, `title`). On another field, for example `duration.unit`, that sentence would be wrong, so it falls back to « Vérifiez ce champ. ».
     - `title` and `documentDate` (SB3) reuse the 160-character and date texts.
     - Every other case → the shared kind text.
   - `recordWarningMessage`: `HEIGHT_UNUSUAL` / `WEIGHT_UNUSUAL` → « Valeur inhabituelle : vérifiez-la. »; an unknown warning → nothing shown.
9. **`ApiFieldErrorKind.duplicate`** is added to the shared parser (`DUPLICATE` → `duplicate`) with the generic text « Cet élément figure déjà dans la liste. ». Before, it read as `invalid`. The only switch over this enum (`apiFieldErrorMessage`) was updated; the parser test lists the new kind.
10. **No value in logs.** The data layer logs nothing. Every draft, form, source, item and document `toString` carries no label, name, title or file name. `ApiFailure.logSummary` already carries codes only.

## 4. Contract used by the app (A2, A4)

**Section saves** (`MedicalRecordWriteRepository`):
- **Every call takes:** `subject`, `expectedVersion`, a `SaveAttempt` and an optional `CancelToken`.
- **Result:** `Result<SectionSaved{section, version, warnings}>`.

| Method | Request | Body sent |
|---|---|---|
| `saveBloodType(bloodType)` | `PUT /me/medical-record/life-safety/blood-type` | `{value, expectedVersion}` |
| `saveAllergies(items: [AllergyDraft])` | `PUT …/life-safety/allergies` | `{items:[{itemId?, label, severity?}], expectedVersion}` |
| `saveConditions(items: [ConditionDraft])` | `PUT …/life-safety/conditions` | `{items:[{itemId?, label}], expectedVersion}` |
| `saveMeasurements(heightCm?, weightKg?)` | `PUT …/body-measurements` | `{heightCm?, weightKg?, expectedVersion}` |
| `saveDeclaredMedications(items: [DeclaredMedicationDraft])` | `PUT …/medications/declared` | `{items:[{itemId?, name, dosageText?, timesPerDay?, duration?{value, unit}, startedOn? "YYYY-MM-DD"}], expectedVersion}` (`expectedVersion` = the page's `listVersion`) |

- **Every PUT:** query `subject=SELF|FAMILY:{id}`; headers `Idempotency-Key`, `Cache-Control: no-store`; it can be replayed after a token refresh.
- **Never sent:** nulls, `authorType`, `source`.
- **Rules A2 must follow:** an own item kept → its `itemId`; a PROFESSIONAL item → never sent (the server keeps it); `items: []` → « Aucune ».

**Documents** (`MedicalDocumentRepository`):

| Method | Request | Result |
|---|---|---|
| `documents(subject, cursor?)` | `GET /me/medical-record/documents?subject&size=20&cursor?` | `MedicalDocumentPage{items, nextCursor}` |
| `status(subject, documentId)` | `GET …/documents/{id}/status` | `MedicalDocument` (poll while `isProcessing`) |
| `upload(subject, source, form{title, type, documentDate?}, attempt, onSendProgress?)` | `POST …/documents` multipart (`file`, `title`, `documentType`, `documentDate?`), key, 2 min send timeout | `UploadedDocument{documentId, status}`, **or a local refusal with no request** |
| `delete(subject, documentId, attempt)` | `DELETE …/documents/{id}`, key | `Result<void>` (204) |
| `openViewSession(subject, documentId)` | `POST …/documents/{id}/view-sessions` | `DocumentViewSession{viewSessionId, pageCount, expiresAt}` |
| `fetchPage(subject, documentId, session, pageNumber)` | `GET …/view-sessions/{sid}/pages/{n}` (bytes) | `FetchedDocumentPage{session, page{pageNumber, png}}`; on a 410, one silent new session |

## 7. Risks, open points, not done

1. **Web upload memory.** On web, the file is read through a stream, but a browser request cannot be streamed: Dio's browser adapter puts together the whole multipart body before it sends it, so up to 15 MB is held once, during the send. Mobile and desktop stream from disk. That is a platform limit, not a choice. A4 should build the source from `XFile.openRead()` (a fresh stream per call), not `PlatformFile.bytes`.
2. **`StreamDocumentSource.sizeBytes` must be the real size.** It becomes the part's length. The picker's size is used, and the server re-checks.
3. **An unknown allergy severity** (a future server value) is read as `AllergySeverity.unknown` and **not sent back**. So if the editor re-saves that item without the patient touching it, MRS would drop the severity. Today MRS only has MILD, MODERATE and SEVERE, so this cannot happen yet. A2 should keep a PROFESSIONAL item out of the body anyway.
4. **The old documents client** (`core/api/documents_api.dart`, `MedicalDocumentsScreen`, `MedicalDocumentUploadController`) still uses the `?patientId=` routes and a 20 MB limit. A4 moves the tab to this repository; the old client and routes are then retired (SB3 §7.9).
5. **Not done in A1, by design:**
   - the editor and its local checks (A2);
   - the documents tab, status polling and the viewer (A4);
   - wiring in `main.dart` (with the view models in A2/A4).
