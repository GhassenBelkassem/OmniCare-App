# G2.1-B6b — Onboarding and Ma Santé send all conditions

Date: 2026-11-12 · Repo: OmniCare-BackEnd only · Follows: G2.1-B6 (§4.3), G2.1-SB2 (STOP 3)

## 1. Decision applied

CTO decision of 2026-11-12: from now on, onboarding saves **every** condition, not only those marked critical. This is acceptable because every environment holds test accounts only.

**Release blocker, still open:** the doctor views must hide non-critical conditions outside full-passport consent before any real patient is onboarded. This means G-1 switching the workspace and chart to `records.ReadLifeSafetyAlwaysVisible` (B6 report §4.2). Until then, a treating doctor sees every condition, critical or not.

## 2. What changed

| Flow | Before (B6) | Now (B6b) |
|---|---|---|
| Onboarding step 3 | only `criticalOptIn=true` conditions saved, each `critical=true` | **every** condition saved; `criticalOptIn` true → `critical=true`, false → `critical=false` |
| Onboarding step 3, condition sent again | — | the patient's opt-in is sent; MRS changes a kept condition's flag only when it differs, so an unchanged condition keeps its flag |
| Ma Santé (`PATCH /profile/medical-data`) | new → `critical=true`; kept → no flag (keeps its own) | unchanged |
| « Dossier médical » editor (SB1 `PUT …/conditions`) | no flag sent; `critical` in the app body → 400 | unchanged |
| « Aucune » (`noKnownConditions`) | NONE_KNOWN | unchanged |
| Empty conditions list, no « Aucune » | nothing written | unchanged: an empty answer isn't « none » |

## 3. Files

- `patientrecord/application/PatientMedicalDataWriteService.java`
  - The internal overload now takes `List<Boolean> flags`, one flag per item (`null` means no flag), in place of the B6 `boolean newItemsCritical`.
  - The editor overload passes `null`.
  - The flag list is server-made only. No DTO carries it.
- `patientrecord/application/PatientMedicalDataUpdates.java`
  - New `ConditionInput(label, critical)` and `conditionsWithOptIn(...)` for onboarding.
  - `conditions(...)` (Ma Santé) keeps "new → true, kept → no flag".
  - Both share `writeConditions`, so the label matching, professional-item skip and field-error renaming stay the same.
- `profile/service/OnboardingService.java`
  - Step 3 drops the opt-in filter and maps each `ConditionDto` to `ConditionInput(name, criticalOptIn)`.
  - The class javadoc is updated.
- Tests:
  - `profile/service/CriticalConditionsTest.java` (+4 tests, 1 replaced).
  - `profile/service/OnboardingServiceTest.java`: the test that pinned "non-critical never written" is replaced by "every condition written with its opt-in".
  - `patientrecord/PatientMedicalRecordControllerWebMvcTest.java` (+1 test).

## 4. Tests

| Required case | Test |
|---|---|
| Onboarding with a non-critical condition → readable with `critical=false` | `CriticalConditionsTest.aNonCriticalOnboardingConditionIsReadableWithCriticalFalse`: status LIST, label in `criticalConditions`, item `critical=false`, author PATIENT |
| A critical one → `critical=true` | `aCriticalOnboardingConditionIsReadableWithCriticalTrue` |
| Mapping true→true, false→false, all sent | `onboardingSendsEveryConditionWithItsOptInAsTheFlag`: checks the body sent to MRS and the read |
| A kept, unchanged condition keeps its flag | `anOnboardingConditionSentAgainUnchangedKeepsItsFlag`: 2 real writes, same item ids, same flags |
| A Ma Santé save doesn't flip an existing flag | `aMaSanteSaveNeverFlipsAnOnboardingFlag`: kept items are sent with no flag and stay false/true; a new one is true. The B6 `aMaSanteSaveNeverPromotesAnEditorCondition` test still passes |
| `GET /me/medical-record/medical-data` JSON | `PatientMedicalRecordControllerWebMvcTest.theMedicalDataReadCarriesEachConditionFlag`: `conditionItems[n].critical` is false, true, and true for an MRS item with no flag |
| The editor body never accepts `critical` | the existing B6 tests in `PatientMedicalRecordWriteControllerWebMvcTest` (400, no MRS call), unchanged and green |

How the tests run: the onboarding tests go through the real `OnboardingService`, `PatientMedicalDataUpdates`, `PatientMedicalDataWriteService` and `PatientMedicalRecordService`, over the in-memory MRS, which applies the B6 flag rules.

Result: full Spring suite `./mvnw test`, **3197 tests, 0 failures, 0 errors, 2 skipped**. A first run while another chat was editing `doctortemplate` showed 17 errors in that chat's classes; the re-run after it finished is fully green. No MRS change, so no Go run is needed.

## 5. Manual test steps for the CTO

1. Create a new patient account in the app and start onboarding.
2. At the conditions step, add « Asthme » and leave it **not** marked critical. Finish onboarding.
3. Open « Dossier médical » → « Asthme » is listed under the conditions.
4. Optional: repeat with a second new account, marking « Asthme » critical. It shows the same way. The flag isn't shown in V1; A2 will read it.
5. Optional: in Ma Santé, save the conditions without changing them. « Asthme » is still listed, and its flag hasn't changed (not visible in V1).

## 6. Risks and follow-ups

- **Release blocker (G-1):** hide non-critical conditions in the doctor views outside full-passport consent, and land B4 (a consultation write that keeps the v3 flag) first. Until both land, accounts must stay test-only. The full-passport consent definition (B6 report §4.4) is still a CTO decision.
- A consultation that changes life-safety data still rewrites conditions as v2, so the flags read back as critical (B6 report, P1 for B4). This leaks nothing today, since doctors see every condition anyway.
